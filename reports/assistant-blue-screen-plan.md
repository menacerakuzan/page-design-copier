# План: «синій екран» після закриття ІІ-асистента

## Симптом
Відкриття `/asystent` працює. Після закриття (стрілка «назад» у хедері → `/`,
або свайп-назад) — суцільний синій екран, лікується лише перезавантаженням
сторінки. Баг повторний: одна спроба фіксу вже була (гонка PanelColor з
cleanup у `AssistantPage` — виправлена, коментар у `AssistantPage.tsx:48-63`),
але проблема залишилась.

## Що вже з'ясовано (НЕ повторювати)
1. **jsdom-репродукція НЕ ловить баг**: рендер `<App/>` на `/asystent`, клік
   по кнопці «назад» (`aria-label="На головну"`) → Index рендериться повністю,
   жодного крашу. Отже це НЕ помилка React-рендера, яку видно в тестах —
   баг специфічний для реального браузера (найімовірніше iOS Safari — вся
   попередня історія цього бага була про Safari).
2. «Синій» = `#001a3d` — фон `html`/`body` (index.css:108-115 + inline-скрипт
   в index.html). Чистий синій екран означає: **контент React живий у DOM або
   ні, але НЕ малюється поверх фону**. Перезавантаження лікує → зламаний стан
   живе в документі (стилі/атрибути body, компоситор, зсув viewport), а не в
   даних.
3. `ErrorBoundary` (src/components/ErrorBoundary.tsx) обгортає ЛИШЕ `<Routes>`.
   `MobileNav`, `AssistantFab`, `BackgroundMusicPlayer`, `KonamiEasterEgg`
   рендеряться ПОЗА boundary (App.tsx:108-112) — краш у будь-якому з них
   розмонтовує ВСЕ дерево до голого синього body. Це підтверджений клас
   ризику, навіть якщо не він стріляє зараз.
4. У проєкті два Radix-діалоги на цьому флоу: шторка меню в `MobileNav`
   (через неї відкривають асистента: клік по посиланню одночасно закриває
   Sheet і навігує) і шторка історії в `AssistantPage`. Radix використовує
   `react-remove-scroll` (ставить `overflow`/`data-scroll-locked` на body) і
   пакет `aria-hidden` (ставить `aria-hidden`/`inert` на сусідів порталу,
   тобто на весь контент `#root`). Відомий клас багів: якщо діалог
   розмонтувати посеред exit-анімації (навігація/свайп-назад), ці атрибути
   **протікають** і лишаються назавжди → сторінка невидима для рідера/
   заморожена для тапів, «лікує тільки перезавантаження».
5. iOS-специфіка `AssistantPage`: `h-[100dvh]`, textarea з клавіатурою,
   `resetScroll` onBlur (коментар у файлі: Safari скролить сторінку при
   фокусі і не повертає). Якщо закривати асистента ПРИ ВІДКРИТІЙ КЛАВІАТУРІ,
   Safari може лишити visual viewport зі зсувом уже на головній → контент
   відрендерений, але ВЕСЬ над видимою областю → видно лише синій фон.
   `ScrollToTop` скролить на 0 синхронно з навігацією, ДО того як анімація
   ховання клавіатури завершилась — Safari може перезаписати скрол після.

## Порядок дій

### Крок 0 — уточнити в користувача (одним повідомленням, AskUserQuestion)
Без цього не вгадаємо між гіпотезами:
- Пристрій/браузер (iPhone Safari? Android Chrome? десктоп?).
- Як саме закриває: стрілка «назад» у хедері асистента / системний свайп-назад /
  щось інше.
- Чи була відкрита клавіатура в момент закриття; чи повторюється, якщо
  відкрити асистента і закрити ОДРАЗУ, нічого не друкуючи.
- На синьому екрані: чи реагує сторінка на тапи/скрол взагалі; чи видно
  бодай щось (лого, текст, таб-бар знизу).

### Крок 1 — захисні фікси (робити ВСІ, кожен закриває реальний клас відмов)

**1a. «Прибиральник» на зміну маршруту** — в `App.tsx` розширити `ScrollToTop`
(або окремий компонент поруч) ефектом на `pathname`, який знімає протеклі
блокування від Radix/remove-scroll:
```ts
useEffect(() => {
  // Протечки Radix Sheet при розмонтуванні посеред exit-анімації
  document.body.style.removeProperty("pointer-events");
  document.body.style.removeProperty("overflow");
  document.body.removeAttribute("data-scroll-locked");
  // aria-hidden/inert, які пакет aria-hidden ставить на дітей #root
  document.querySelectorAll("[data-aria-hidden]").forEach((el) => {
    el.removeAttribute("aria-hidden");
    el.removeAttribute("data-aria-hidden");
    el.removeAttribute("inert");
  });
}, [pathname]);
```
УВАГА: власні лайтбокси (GalleryLightbox, ReelLightbox) теж ставлять
`body.style.overflow` — але вони розмонтовуються при навігації, тож зняття
на зміні pathname безпечне. НЕ чіпати цей стан поза зміною маршруту.

**1b. ErrorBoundary навколо глобального хрому** — в `App.tsx` обгорнути
`MobileNav`, `AssistantFab`, `BackgroundMusicPlayer`, `KonamiEasterEgg`
окремими маленькими boundary (окремими — щоб краш одного не ховав решту;
fallback = null, тихо). Мета: краш поза `<Routes>` більше ніколи не зносить
все дерево до голого синього body.

**1c. iOS viewport після клавіатури** — два маленькі фікси:
   - В `AssistantPage` на кнопці «назад» (Link, рядок ~123) додати
     `onClick={() => taRef.current?.blur()}` — явний blur ДО навігації.
   - В `ScrollToTop` (App.tsx) додати відкладене повторне скидання скролу:
     `setTimeout(() => window.scrollTo(0, 0), 400)` після основного —
     переживає анімацію ховання клавіатури Safari. Обережно: НЕ ламати
     позицію скролу, якщо користувач уже почав скролити — можна перевіряти
     `window.scrollY` і скидати тільки якщо документ «застряг» вище нуля при
     фактичному верху (або обмежитись переходами З `/asystent`:
     зберігати попередній pathname у ref).

### Крок 2 — верифікація і деплой
`npx tsc --noEmit` → `npx vitest run` → `npm run build` → перевірити хеш
бандла: `curl -sk https://tourism.od.gov.ua/ | grep -o 'assets/index-[^"]*\.js'`
(nginx роздає прямо з dist/, окремого деплой-кроку немає).
Попросити користувача відтворити баг на пристрої ще раз.

### Крок 3 — якщо баг лишився: інструментація на пристрої
Додати тимчасовий діагностичний режим за query-прапорцем `?debug`:
- підключити eruda (мобільна devtools-консоль) динамічним import з CDN НЕ
  вийде (якщо є CSP) — тоді просто маленький власний оверлей, який показує:
  `window.onerror` / `unhandledrejection` повідомлення,
  поточні inline-стилі й атрибути `document.body`,
  `window.scrollY`, `visualViewport.offsetTop/height`,
  наявність `[data-aria-hidden]`/`inert` елементів.
- Користувач відтворює баг з `?debug` і показує скріншот оверлею — далі фікс
  стає очевидним (яка з гіпотез стрельнула).
- Після фіксу діагностичний код ПРИБРАТИ.
